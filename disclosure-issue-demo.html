Screen Reader Disclosure Button Failure Lab

This page demonstrates several real-world accessibility bugs involving disclosure buttons, screen readers, keyboard interaction, and accessibility APIs.

Each section contains:

  • A broken implementation
  • An explanation of why it fails
  • A live demo
  • Inspectable code behavior for DevTools analysis

1. Correct Native Button Implementation

This is the correct implementation using a native <button>.

This disclosure uses native semantics and works properly with keyboard, screen readers, accessibility APIs, and synthesized click events.
Why this works:
  • Native button semantics
  • Automatic Enter/Space handling
  • Accessible activation events
  • No custom keyboard traps

2. Fake Button Using Only Keydown

Expected failure: Works without screen reader. May fail in NVDA browse mode or VoiceOver interaction differences.

About
This disclosure relies entirely on keydown events. Screen readers may intercept Enter or Space before the page receives it.

3. Deprecated Keypress Event

Expected failure: Inconsistent behavior across browsers and screen readers.

About
This disclosure uses the deprecated keypress event. Some browser and screen reader combinations never fire it.

4. Native Button Broken With preventDefault()

Expected failure: Native button semantics sabotaged by JavaScript.

This button SHOULD work because it is native. However, JavaScript blocks default activation behavior.

5. Invisible Overlay Stealing Interaction

Expected failure: Interaction inconsistencies caused by hidden overlay interception.

An invisible positioned layer intercepts interaction. This often happens accidentally in enterprise UI frameworks.

6. Pointer Events Disabled

Expected failure: Keyboard may work while screen reader activation fails.

pointer-events:none disables click interaction. Some screen readers synthesize click events which now fail.
